# Module 13 — Part 1 Capstone

## Goal
Build a production-grade standalone Jenkins setup from scratch using everything you've learned in Part 1. The result should be reproducible: anyone with the Git repos can stand it up again.

## Scenario
You are the new platform engineer at Acme Inc. Acme has:
- 3 Java/Maven microservices in 3 GitHub repos.
- A small ops team that wants automation but trusts no untested change.
- One Linux VM available for the Jenkins controller, two more for build agents (one Linux, one Windows).

You will deliver a complete CI/CD platform on this fleet.

## Deliverables Checklist

### 1. Controller infrastructure
- [ ] Linux VM provisioned (firewall, updates).
- [ ] Java 17 installed.
- [ ] Jenkins LTS installed and running as a service.
- [ ] Nginx reverse proxy with valid TLS certificate.
- [ ] Jenkins URL configured to the HTTPS hostname.

### 2. Configuration as Code
- [ ] `jenkins-config` Git repo containing:
  - `jenkins.yaml` (JCasC)
  - `plugins.txt`
  - `seed/jobs.groovy` (Job DSL)
  - `Dockerfile` *(optional, if running Jenkins in a container)*
  - `README.md` with operating procedures
- [ ] Controller pulls config from this repo; UI changes are forbidden by convention.
- [ ] JCasC reload tested without restart.

### 3. Plugins
- [ ] Plugins pinned by version in `plugins.txt`.
- [ ] Plugin set includes everything the team uses; no extras.
- [ ] Plugin update procedure documented.

### 4. Standalone agents
- [ ] Linux SSH agent registered with labels `linux docker maven`.
- [ ] Windows JNLP agent registered with labels `windows`.
- [ ] Agents declared in JCasC.
- [ ] Tool installations (JDK 17, Maven 3.9, Node 20) defined in JCasC.
- [ ] Workspace cleanup job runs weekly on each agent.

### 5. Source Code Management
- [ ] GitHub credentials (App or PAT) stored in the credentials store.
- [ ] Webhook from GitHub to Jenkins working — build triggers within seconds of a push.
- [ ] One **Multibranch Pipeline** per microservice, generated by the Job DSL seed.

### 6. Shared Library
- [ ] `pipeline-library` Git repo with:
  - `vars/javaService.groovy` — the team's pipeline template.
  - `vars/notifySlack.groovy` — Slack notifications.
  - `vars/deploySsh.groovy` — SSH deploy step.
- [ ] Library registered as a Global Pipeline Library, default version `main`.
- [ ] Tag `v1.0.0` exists; one consuming pipeline pins to it.

### 7. Application Pipelines
Each microservice repo contains a one-page `Jenkinsfile` like:
```groovy
@Library('acme-ci@v1.0.0') _
javaService(appName: 'payments-api')
```
The library template handles checkout, build, parallel verify (unit + lint), publish to Nexus on `main`, and SSH deploy to a "staging" VM.

- [ ] All three microservice pipelines green on `main`.
- [ ] A feature-branch failure does not affect `main`.
- [ ] JUnit results published; trend graph visible.
- [ ] Slack `#builds` channel receives success/failure notifications.

### 8. Deployment & Release
- [ ] Build → publish → deploy-to-staging happens automatically on `main`.
- [ ] Promotion to production requires an `input` approval step.
- [ ] Deploys use SSH against a target VM; smoke test (`/health`) follows the deploy.
- [ ] Rollback is a parameterized job (`deploy-prod`) that takes a version string.
- [ ] Successful prod deploys tag the Git commit.

### 9. Documentation (in the `jenkins-config` repo)
- [ ] Architecture diagram (controller, agents, networks).
- [ ] Runbook: plugin and core upgrade.
- [ ] Onboarding doc for a new microservice (5 steps or fewer).

## Acceptance Tests

Run each of these on the completed setup:

1. **Bootstrap test.** Take a clean VM, run your bootstrap process. Within 30 minutes you should have a working Jenkins identical to the original.
2. **Push test.** Push a commit to any microservice's `main`. Within 2 minutes the build is green and a notification arrives.
3. **PR test.** Open a PR with a failing test. The PR build goes red without affecting `main`.
4. **Rollback test.** Promote `v1.4.7` to prod. Then run `deploy-prod` with version `v1.4.6`. Verify the old version is back online and tagged in Git.
5. **Agent failure test.** Reboot the Linux agent during a build. The build fails cleanly (no zombie state). Subsequent builds run on the same agent once it reconnects.

## Stretch Goals (optional)

- Add a Windows microservice and verify the matrix label routing.
- Add a `nightly-cleanup` job that prunes Docker images and old artifacts.
- Add a `library-smoke` repo whose only job is to exercise every public step in `pipeline-library`. Tag the library only after this is green.
- Add **Lockable Resources** for the production environment so two simultaneous prod deploys serialize.

## Reflection Questions

When you're done, write a short reflection:
- What's the *highest-risk* part of this setup? What would you change to reduce that risk?
- If a stranger joined the team tomorrow, what would they need to learn first? Is it documented?
- Which manual UI clicks remain? How would you eliminate them?
